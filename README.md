# HTTP/1.1 Request Parser

An educational HTTP/1.1 server and request parser implemented from scratch in Node.js using the low-level `net` module, without relying on Node.js's built-in `http` module or external web frameworks. It handles raw TCP byte streams, accumulates fragmented chunks, detects header boundaries via a byte-level finite-state machine, parses request lines and header fields via lookup tables and a trie, and frames request bodies using `Content-Length`. It validates protocol syntax and answers requests having `Content-Length: 0` with a `204 No Content` response, but it lacks application response routing, chunked transfer decoding, and HTTP-level error status responses.

## Status

### Implemented
- Raw TCP server listening on port 3000 via `net.createServer`.
- Cross-chunk CRLFCRLF (`\r\n\r\n`) header boundary detection using a 4-state byte-level finite-state machine.
- Chunk accumulation buffer maintaining incoming `Buffer` references prior to header boundary identification.
- Maximum header size threshold enforcement (`MAX_HEADER_BYTES = 8192` bytes) protecting against oversized headers.
- Request-method parsing for `GET`, `POST`, `PUT`, `PATCH`, and `DELETE` using a nested-switch prefix trie (originally generated by a script, then edited by hand).
- Origin-form request-target validation (`/path`) using a 256-entry lookup table (`ALLOWED_TARGET_BYTES`).
- HTTP version parsing and validation for `HTTP/1.0` and `HTTP/1.1` (`parseVersion`, handwritten).
- Header field-name token grammar validation using a 256-entry lookup table (`ALLOWED_FIELD_KEY_BYTES`), with lowercase normalization.
- Strict colon syntax verification rejecting leading whitespace before the header colon (RFC 9112 §5.1).
- Header field-value parsing with single-pass stripping of leading and trailing optional whitespace (SP and HTAB) via a 3-way byte lookup table (`ALLOWED_FIELD_VALUE_BYTES_AND_SKIPPING_SP_AND_OWS`).
- Duplicate header rejection via `Object.hasOwn` checks (a deliberately strict design decision; see Algorithms and data structures).
- Mandatory `Host` header enforcement on `HTTP/1.1` requests (RFC 9112 §3.2).
- Mutual exclusivity enforcement between `Transfer-Encoding` and `Content-Length`, destroying connections containing both (RFC 9112 §6.1, §6.3).
- Rejection of `Transfer-Encoding` on `HTTP/1.0` requests.
- Numerical validation of `Content-Length` via `/^\d+$/` and maximum body limit verification (`MAX_BODY_BYTES = 10485760` bytes; an arbitrary example value, not a protocol limit).
- Immediate `HTTP/1.1 204 No Content\r\n\r\n` response and state reset for requests specifying `Content-Length: 0`.
- Body assembly across single or multiple TCP chunks for requests with `Content-Length > 0`, logging the completed `Buffer` payload to stdout.
- Zero-copy slicing of leftover bytes across message boundaries using `Buffer.subarray`.

### Not implemented / known limitations
- `Transfer-Encoding: chunked` body parsing: The execution branch exists as a code stub and does not decode chunk-encoded streams.
- Other transfer codings: Codings such as `gzip`, `deflate`, or `compress` are unhandled.
- Real HTTP response generation: The server only emits an HTTP response (`204 No Content`) when `Content-Length` is explicitly `0`. Requests with bodies (`Content-Length > 0`) or requests without bodies (such as standard `GET` requests) do not receive an HTTP response; payloads are logged to the console while the client connection remains open.
- HTTP error responses: Protocol syntax violations, invalid methods, malformed versions, missing `Host` headers, duplicate headers, or exceeded size limits immediately invoke `socket.destroy()` (often issuing a TCP RST) rather than returning formatted HTTP 4xx or 5xx responses (such as `400 Bad Request`, `414 URI Too Long`, `431 Request Header Fields Too Large`, `411 Length Required`, or `505 HTTP Version Not Supported`).
- HTTP pipelining: When residual bytes belonging to a subsequent request arrive in the same TCP chunk, they are preserved in `chunksArr`, but the parser does not loop within the active event tick to parse the next request. Processing remains suspended until the next socket `data` event fires.
- Request state lifecycle: The `req` object is scoped to the socket connection closure and only reallocates upon encountering a new header. It is not cleared when payload assembly completes, causing properties like `req.payload` to persist until the next header parse. Requests lacking both `Content-Length` and `Transfer-Encoding` reset internal buffer pointers but return no response.
- HTTP method coverage: Only five methods (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`) are recognized. Other standard RFC methods (`HEAD`, `OPTIONS`, `CONNECT`, `TRACE`) trigger immediate socket destruction.
- URI request target forms: Only origin-form targets beginning with `/` are accepted. Asterisk-form (`*`), absolute-form (`http://...`), and authority-form URIs trigger connection teardown.
- Obsolete line folding (obs-fold): Multiline headers containing leading whitespace on continuation lines are rejected via `socket.destroy()` instead of a `400` response (RFC 9112 §5.2 requires either a 400 response or replacement of the fold with spaces).
- Stream backpressure: Chunks are continuously accumulated in memory without invoking `socket.pause()` or coordinating with stream drain events.
- No read/idle timeout: A client can hold a connection open indefinitely by sending a partial request slowly.
- No automated tests; verified manually with `curl` only.

## How to run

Requires a Node.js version that supports `Object.hasOwn` (Node.js 16.9 or later). Start the server from the project folder:

```bash
node buffer.js
```

The server binds to port 3000 and outputs:
```
server is listening on port 3000!!
```

`curl` adds the `Host` header automatically. On Windows PowerShell use `curl.exe` (plain `curl` is an alias for another command) and keep each command on a single line.

### Sending a POST request with a payload

```bash
curl.exe -v -X POST http://localhost:3000/submit -H "Content-Type: text/plain" --data-binary "Sample payload data"
```

The server accumulates the body chunks, concatenates the payload, and logs the resulting `Buffer` to stdout. Because response generation is not implemented for requests with non-zero payloads, `curl` will wait for a response until terminated.

### Testing an empty POST request

To observe the server's implemented HTTP response (`204 No Content`), send a request with `Content-Length: 0`:

```bash
curl.exe -v -X POST http://localhost:3000/empty -H "Content-Length: 0"
```

Expected output includes:
```
< HTTP/1.1 204 No Content
```

## What I built

The request processing pipeline executes across the following phases, all inside the `socket.on('data', ...)` handler in `buffer.js`:

1. **Socket `data` events**: The server initializes a TCP listener via `net.createServer`. Each network read delivered to user space triggers a `data` event on the client socket, providing a `Buffer` chunk.
2. **Chunk accumulation**: Incoming chunks are pushed into `chunksArr`, and their byte counts are added to `totalBytes`. This preserves chunk references without copying data.
3. **Header-end detection**: While `isHeaderFound` remains `false`, the chunk is scanned byte-by-byte using a 4-state finite-state machine (the `state` variable) looking for `\r\n\r\n`. Upon reaching the final state, `absoluteLastCRLFCRLFByte` is computed, trailing bytes are sliced into `unknownEntity` via zero-copy `Buffer.subarray`, the header chunks are concatenated into a unified `header` Buffer, and `isHeaderFound` is marked `true`. If no terminator is found, the handler returns and waits for the next chunk.
4. **Request-line parsing**:
   - The method is parsed by `parseMethod` (`generated-parser.js`) using a byte-level switch trie.
   - The request target is checked for a leading `/` and scanned until an ASCII space (`0x20`), validating each byte against `ALLOWED_TARGET_BYTES`.
   - The HTTP version is parsed by `parseVersion` (`generated-parser.js`), confirming `HTTP/1.0` or `HTTP/1.1` followed by `\r\n`.
5. **Header-field parsing**: The server iterates through remaining header bytes until `absoluteLastCRLFCRLFByte - 1`:
   - Field names are validated against `ALLOWED_FIELD_KEY_BYTES`.
   - The colon character (`0x3A`) must directly follow the key; preceding whitespace triggers socket destruction. Keys are normalized to lowercase.
   - Leading optional whitespace is skipped via `ALLOWED_FIELD_VALUE_BYTES_AND_SKIPPING_SP_AND_OWS`.
   - Value bytes are scanned and trailing whitespace is trimmed using the 3-value lookup scheme.
   - Each field line must end with `\r\n`. Duplicate header names trigger immediate connection teardown via `Object.hasOwn`.
6. **Body framing by Content-Length**:
   - For `HTTP/1.1`, the presence of a `Host` header is verified.
   - Requests containing both `Transfer-Encoding` and `Content-Length`, or `Transfer-Encoding` on `HTTP/1.0`, are rejected.
   - If `Content-Length` is present, it is validated for digits (`/^\d+$/`) and parsed into `expectedPayloadLength`.
   - When `Content-Length === 0`, the server transmits `HTTP/1.1 204 No Content\r\n\r\n` and resets parser variables.
   - When `Content-Length > 0`, the parser sets `header = undefined` to transition to payload assembly mode and consumes available bytes from `unknownEntity`.
   - Subsequent `data` events append incoming chunks directly to `payloadArr` until `expectedPayloadLength` reaches 0 (the final `else` branch of the handler).
7. **Size limits**: The cumulative header size is compared against `MAX_HEADER_BYTES` (8192 bytes) during chunk arrival and at boundary detection. The declared payload size is compared against `MAX_BODY_BYTES` before any body is buffered. Violations destroy the socket.
8. **State reset**: Upon completing payload assembly or handling a zero-length request, parsing flags (`isHeaderFound`, `state`, `expectedPayloadLength`, `absoluteLastCRLFCRLFByte`, `payloadArr`) are cleared. Surplus bytes past the payload boundary are sliced into `chunksArr` via `Buffer.subarray` for subsequent processing.

## Algorithms and data structures

### Byte-level finite-state machine for CRLFCRLF detection
- **What it is**: A deterministic 4-state automaton tracking sequential occurrences of Carriage Return (`\r`, `0x0D`) and Line Feed (`\n`, `0x0A`).
- **Where it is**: the `if (!isHeaderFound)` scanning loop in `buffer.js`, driven by the `state` variable.
- **Why it was chosen**: TCP segment boundaries do not align with HTTP delimiters; the delimiter `\r\n\r\n` can split across consecutive reads (e.g., `\r\n\r` in one chunk, `\n` in the next). The FSM maintains matching state across chunk boundaries without concatenating buffers prematurely or rescanning previously processed bytes.

### 256-entry Uint8Array lookup tables for byte classification
- **What it is**: Flat direct-indexed byte arrays (`Uint8Array(256)`) mapping byte values (0-255) to character classification categories.
- **Where it is**: the top of `buffer.js` (`ALLOWED_TARGET_BYTES`, `ALLOWED_FIELD_KEY_BYTES`, `ALLOWED_FIELD_VALUE_BYTES_AND_SKIPPING_SP_AND_OWS`).
- **Why it was chosen**: Direct array indexing provides O(1) byte classification with no regular expression overhead. The 3-way scheme in `ALLOWED_FIELD_VALUE_BYTES_AND_SKIPPING_SP_AND_OWS` (0 = invalid, 1 = visible characters/obs-text, 2 = whitespace SP/HTAB) enables single-pass scanning and trimming of leading and trailing optional whitespace (OWS) without backtracking or substring allocations.

### Nested-switch trie for method matching
- **What it is**: A character prefix tree (trie) compiled into nested JavaScript `switch` statements matching method bytes sequentially.
- **Where it is**: `parseMethod` in `generated-parser.js`.
- **Provenance**: The trie was originally produced by `methodGenerator.js` (a trie-to-switch code generator), then edited by hand. The interface of the current file differs from the generator's output (it writes into `req` instead of `parsedData` and uses a named export), and `parseVersion` is handwritten, so the file cannot be reproduced from the generator as-is.
- **Why it was chosen**: Matches valid methods (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`) in O(L) time where L is the token length. It avoids string allocations, regex execution, and hash lookups on raw byte streams, destroying the socket immediately upon the first invalid character.

### Pointer-based parsing over a single Buffer
- **What it is**: Cursor-driven traversal using integer index offsets (`req.pointer`) directly across raw memory buffers.
- **Where it is**: the request-line and header-field parsing in `buffer.js`, and both functions in `generated-parser.js`.
- **Why it was chosen**: Validates protocol grammar directly against binary memory, avoiding intermediary V8 heap string allocations until syntactic tokens are validated.

### Buffer.subarray zero-copy slicing vs. Buffer.concat copying
- **What it is**: Offset-based view creation (`Buffer.subarray`) versus contiguous memory allocation and copying (`Buffer.concat`).
- **Where it is**: `unknownEntity` extraction, payload boundary slicing, and the `Buffer.concat` calls for `header` and `req.payload` in `buffer.js`.
- **Why it was chosen**: `Buffer.subarray` creates a view over existing memory without copying bytes, used for extracting residual bytes (`unknownEntity`) and framing payload boundaries. `Buffer.concat` is executed only when a complete segment (the full header block or full body) must be assembled into a single contiguous buffer.

### Array of chunk references as accumulation buffer
- **What it is**: An in-memory JavaScript array (`chunksArr`) appending references to incoming `Buffer` instances.
- **Where it is**: `chunksArr` in `buffer.js`.
- **Why it was chosen**: Appending references to an array avoids copying on every incoming read. Progressively concatenating buffers on every chunk would cause repeated reallocation and excessive garbage collection overhead.

### Header-size and body-size limits as DoS protection
- **What it is**: Hard thresholds on cumulative header bytes (`MAX_HEADER_BYTES = 8192`) and declared payload size (`MAX_BODY_BYTES = 10485760`).
- **Where it is**: `MAX_HEADER_BYTES` and `MAX_BODY_BYTES` constants and their checks in `buffer.js`.
- **Why it was chosen**: Protects against process out-of-memory crashes by terminating connections that stream indefinite header bytes or declare excessively large payloads before memory is allocated. Limits are enforced server-side, independent of any client-supplied signal. The limit values are arbitrary example choices, not protocol-mandated.

### Duplicate-header rejection
- **What it is**: Single-definition validation enforced via `Object.hasOwn(req.headers, currentKey)`.
- **Where it is**: the header-field parsing loop in `buffer.js`.
- **Why it was chosen**: Rejecting repeated headers removes ambiguity about which value a request means, which reduces the risk of request-smuggling style desynchronization. This is a stricter design decision than the RFC requires: it also rejects requests with repeated list-type fields, which can be valid. The RFC explicitly requires a 400 response for more than one `Host` header (RFC 9112 §3.2).

### Host-header requirement for HTTP/1.1
- **What it is**: Verification that `req.headers['host']` is present on all HTTP/1.1 requests.
- **Where it is**: after header-field parsing in `buffer.js`.
- **Why it was chosen**: Enforces RFC 9112 §3.2, which requires a `Host` header field in all HTTP/1.1 request messages, and that a server respond with 400 to a request lacking one. This implementation destroys the socket instead of responding.

### Rejecting Transfer-Encoding + Content-Length together
- **What it is**: Mutual exclusivity check between `transfer-encoding` and `content-length` headers, and rejection of `transfer-encoding` in HTTP/1.0.
- **Where it is**: the framing decision after header-field parsing in `buffer.js`.
- **Why it was chosen**: RFC 9112 §6.3 treats a message with both headers as a possible smuggling attempt, and §6.1 allows a server to reject it (it must close the connection after responding). It also requires treating an HTTP/1.0 message with `Transfer-Encoding` as faulty framing and closing the connection. This implementation rejects both by destroying the socket.

## Design notes

### Why TCP chunks are not HTTP messages
TCP is a byte-stream transport protocol. It guarantees ordered, reliable byte delivery, but has no awareness of application-layer message boundaries, HTTP headers, or request framing. A single logical HTTP request may arrive fragmented across multiple `data` events, or multiple requests may arrive coalesced within a single `data` event. Application-layer parsers must therefore maintain explicit boundary-detection state across read boundaries.

### Why limits are enforced server-side
Client-controlled signals, such as a connection close or the `Content-Length` header, cannot be trusted for resource management. A misbehaved or malicious client can withhold a close signal or stream unbounded bytes. If a server buffers incoming chunks indefinitely while awaiting a client-provided delimiter, process memory will expand unchecked, eventually terminating the process. The server must measure received bytes per connection and enforce limits itself.

### Why the header limit and body limit are separate
Headers are untrusted protocol metadata that must be buffered and parsed before routing or handler dispatch can take place. Because this happens for every connection, the header limit is kept small (8 KB) to minimize memory exposure. Request bodies carry application payloads that can legitimately require megabytes. Separating the two thresholds allows generous payload capacity while keeping the header phase tightly bounded.
